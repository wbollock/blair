# Blair — Product & Technical Specification

Status: **Draft v1** · Owner: Will Bollock · Last updated: 2026-11-24

Blair is a self-hosted task and notes app in the style of TickTick, Todoist,
Vikunja, tududi and Obsidian Tasks. It is **web-first** and **API-first**: the web
UI is one client of a documented JSON API, and migration scripts or agents, a CLI, and future
native apps use the same API.

This document is the source of truth. Code that changes behavior updates this
spec in the same commit. Decisions with lasting consequences are recorded as
ADRs in [`docs/adr/`](adr/). The build order is in [`docs/PLAN.md`](PLAN.md).

---

## 1. Goals and non-goals

### 1.1 The problem

Every task app I've tried loses tasks at the moment of capture. You type a
task, press Enter, and it disappears into a list you are not looking at, with
no project, no column, and no due date. Filing it later means hunting for it.

**Blair's core promise: a task you just added is never out of reach.** You can
always see it, click it, and file it (project, kanban column, due date,
priority, details) in one or two taps, right after you add it.

### 1.2 Goals (v1)

1. **Fast capture, then fast filing.** Inline quick-add syntax, a "Just added"
   tray of tappable cards, and an Inbox triage mode (§5).
2. **Standard task features done well.** Projects, per-project kanban with
   custom columns mapped to statuses, priority, due date and time, labels,
   checklists (subtasks), markdown in titles and descriptions, search.
3. **Standalone notes.** Quick markdown notes captured from mobile, which can
   be turned into tasks.
4. **In-app reminders and notifications.** No push notifications (§8).
5. **Secure accounts.** User creation with closed or invite registration,
   TOTP 2FA, recovery codes, sessions, scoped API tokens (§9).
6. **A well-documented API.** OpenAPI 3 contract, interactive docs served by
   the app, examples for every endpoint (§10).
7. **Bulk API and export built for migrations by agents.** No built-in
   importers. Instead: batch upsert by external id, writable completion dates,
   dry runs, and a full JSON export that round-trips (§11).
8. **Responsive, clean and beautiful** on desktop and phone. Installable as a
   PWA on iOS Safari, macOS Safari (Add to Dock), Android Firefox and Android
   Chrome. Quick-add works offline (§12).
9. **Simple to run.** One static Go binary or container with SQLite and
   built-in backups.

### 1.3 Non-goals (v1)

These are deliberately out of scope. The data model must not block them.

| Deferred | Notes |
|---|---|
| Recurring tasks | Phase 2. `recurrence` column reserved. |
| Shared projects / collaboration | `owner_id` on every row; ACL table later. |
| Web Push / email notifications | In-app only. SMTP optional later for invites/reset. |
| Full offline editing with conflict resolution | v1 = offline capture queue + read cache. |
| Native iOS/macOS/Android apps | PWA now; the API is ready for SwiftUI later. |
| Attachments, time tracking, calendar sync | Later: read-only ICS feed is a cheap first step. |
| Passkeys / WebAuthn | Phase 2, alongside TOTP. |

### 1.4 Users

v1 targets a single primary user (the admin) on a self-hosted box, but the app
is **multi-user ready**. It supports real accounts, an admin who can create or
invite users, and strict per-user data isolation. Every query is scoped by
`owner_id`, and a test proves that one user cannot read another user's data.

## 2. Glossary

| Term | Meaning |
|---|---|
| **Task** | A unit of work with title, status, optional project/column/due/priority/labels/checklist/description. |
| **Inbox** | Tasks with no project. The default landing place for quick-add. Virtual (not a project row). |
| **Project** | A named container of tasks with its own kanban columns. |
| **Column** | A kanban lane inside a project. Each column maps to exactly one **status**. |
| **Status** | One of `todo`, `doing`, `waiting`, `done`, `cancelled`. Drives completion. |
| **Triage** | Filing an Inbox task: assigning project/column/due/priority, or completing/deleting it. |
| **Just-added tray** | The panel of cards for tasks you created in this session (§5.3). |
| **Note** | A standalone markdown document, not a task. Can be converted to a task. |
| **Notification** | An in-app message (reminder fired, task overdue, security event). |

## 3. Domain model

All IDs are **UUIDv7** strings, generated by the client or the server (ADR-0008).
Timestamps are RFC 3339 UTC. Every user-owned row has `owner_id`, `created_at`,
`updated_at` and an integer `version` for optimistic concurrency (§10.5).

### 3.1 Entities

```
User 1─* Project 1─* Column
User 1─* Task  *─0..1 Project, *─0..1 Column
Task 1─* ChecklistItem
Task *─* Label
Task 1─* Reminder ──fires──> Notification *─1 User
User 1─* Note  *─0..1 Project
User 1─* Session, ApiToken, RecoveryCode, AuditEvent
```

### 3.2 Task

| Field | Type | Rules |
|---|---|---|
| `id` | uuid | Client may supply on create (idempotent; see §10.6). |
| `title` | string 1–500 | Inline markdown subset (§6.1). Required. |
| `description` | string ≤ 100k | Full GFM markdown. |
| `status` | enum | `todo` (default), `doing`, `waiting`, `done`, `cancelled`. |
| `priority` | int 0–4 | 0 none, 1 low, 2 medium, 3 high, 4 urgent. |
| `project_id` | uuid? | null ⇒ Inbox. |
| `column_id` | uuid? | Must belong to `project_id`. null iff `project_id` is null. |
| `due_date` | date? | `YYYY-MM-DD` in the user's timezone. |
| `due_time` | time? | `HH:MM`. Only valid with `due_date`. Absent = all-day. |
| `labels` | uuid[] | User's labels. |
| `position` | string | Fractional index for ordering within column/list (§7.3). |
| `completed_at` | timestamp? | Set when status becomes `done`/`cancelled`. **Writable on create/upsert** (§11). |
| `deleted_at` | timestamp? | Soft delete. Trash purged after 30 days. |
| `external_source`, `external_id` | string? | Origin in another app; unique per owner; upsert key (§11). |
| `recurrence` | string? | Reserved (RRULE) for Phase 2. Rejected in v1. |

Computed (read-only) fields in responses: `checklist_total`, `checklist_done`,
`is_overdue`, `due_at` (UTC instant derived from due date/time and user tz).

### 3.3 Project and Column

Project: `id, name (1–100), color, icon, position, archived_at, description`.

Column: `id, project_id, name (1–50), status, position, wip_limit?`.

**Column ↔ status invariants** (the tududi-style alignment; ADR-0007):

1. Every column maps to exactly one status. Several columns can share a status
   (e.g. *Backlog* and *Next* are both `todo`).
2. A new project gets the default columns **To do** (`todo`), **Doing** (`doing`),
   and **Done** (`done`). The user can rename, add, reorder, or delete them.
3. A project must always have at least one `todo` column and one `done` column.
   The API rejects deleting the last one with `409`.
4. **The column drives the status, and the status finds a column.**
   - **Move to column** ⇒ `task.status = column.status`. Always.
   - **Set status** (e.g. tick the checkbox, or `PATCH status`) ⇒ the task
     moves to the first column (by position) whose status matches. If the
     project has no such column (possible only for `doing`, `waiting`, or
     `cancelled`), the task stays in its current column. Its status is stored
     as set, and the card shows a status badge. This is the only case where
     `task.status != column.status`.
5. Moving a task to another project puts it in the target project's first column
   matching its status, using the same rule. If nothing matches, it goes to the
   first `todo` column (or the first `done` column for `cancelled`).
6. Deleting a column requires a `move_tasks_to` column id (unless it is empty).

### 3.4 Other entities

- **ChecklistItem**: `id, task_id, text (inline md, 1–500), done, position`.
- **Label**: `id, name (unique per user, case-insensitive), color`.
- **Note**: `id, title?, body (GFM), pinned, project_id?, deleted_at`. A note has
  no status or due date. `POST /notes/{id}/convert` creates a task (title = note
  title or first line, description = body) and optionally deletes the note.
- **Reminder**: `id, task_id, remind_at (UTC)`, or a relative reminder
  `offset_minutes` before `due_at` that is recalculated when the due date moves.
  `fired_at`.
- **Notification**: `id, kind, task_id?, title, body, read_at, created_at`.
- **User**: `id, email (unique, normalized), display_name, password_hash, timezone
  (IANA, default from browser at signup), week_start, is_admin, disabled_at,
  totp_secret_enc?, totp_enabled_at?, settings (JSON: default view, theme, etc.)`.
- **Session, ApiToken, RecoveryCode, Invite, AuditEvent**: see §9.

## 4. Information architecture and views

### 4.1 Views

| View | Contents | Notes |
|---|---|---|
| **Inbox** | Tasks with no project, newest first | Badge with count. "Triage" button. |
| **Today** | Due today + overdue (overdue section at top) | Default home. |
| **Upcoming** | Next 14 days, grouped by day, then "Later" | Drag to a day sets the due date (desktop). |
| **Project** | One project. **List** ⇄ **Board** toggle, remembered per project. | List grouped by column. |
| **Label** | Tasks with a label across projects | |
| **Search** | Full-text over tasks, checklists, notes (SQLite FTS5) | `/` hotkey. Filters: status, project, label, priority, due range. |
| **Notes** | Pinned first, then by updated | Masonry/cards on desktop, list on mobile. |
| **Recently added** | Tasks created in the last 7 days | Safety net for "where did it go". |
| **Logbook** | Completed and cancelled tasks, by completion date | |
| **Trash** | Soft-deleted tasks and notes, 30 days | Restore / delete forever. |
| **Triage** | Focused one-at-a-time Inbox filing (§5.4) | |
| **Settings** | Profile, security (password, 2FA, sessions, API tokens), data export, appearance, admin (users, invites) | |

### 4.2 Layout

- **Desktop (≥ 1024 px)**: a collapsible left sidebar (views, projects, labels),
  the main content, and a right **detail drawer** that slides over the content
  when you open a task (the URL updates to `/task/{id}`). The quick-add bar is
  pinned at the top of the main content in every view.
- **Tablet (640–1023 px)**: the sidebar becomes an overlay. The detail drawer
  becomes a full-height sheet.
- **Phone (< 640 px)**: a bottom tab bar with **Inbox · Today · ＋ · Projects ·
  Notes**. The centre **＋** opens the capture sheet (§5.2). Task details open
  as a full-screen route with a back gesture. Tap targets are ≥ 44 px, with
  safe-area insets respected.

### 4.3 Task row / card anatomy

Checkbox (status-aware: ring colour = priority) · rendered title · chips for
due (red if overdue), project/column (only when outside that project), labels,
checklist progress `2/5`, and note/description icon. Tap the row to open
details. On mobile, swipe right to complete and swipe left to open the quick
actions sheet (§4.4).

### 4.4 Quick actions (right-click menu)

One **quick actions** menu changes a task without opening it. The menu has the
same content everywhere. Only how you open it and how it is drawn change.

**Where it is available:** task rows in every list view, kanban cards,
just-added tray cards, triage cards, search results, and Logbook/Trash rows
(which show a reduced set: Reopen/Restore, Delete forever).

**How to open it:**

| Platform | Trigger | Drawn as |
|---|---|---|
| Desktop | Right-click on a row or card | Context menu at the pointer, with submenus |
| Desktop | `⋯` button on row hover, `.` hotkey, `Shift+F10`, or the Menu key on the focused row | Same menu, anchored to the row |
| Phone/tablet | Long-press (≈450 ms, no movement) on a row or card, or the `⋯` button | Bottom sheet; submenus slide in as pages with a back arrow |
| Phone | Swipe left on a list row | Same bottom sheet |

**Menu contents** (in this order, with keyboard accelerators shown):

1. **Open** `Enter`
2. **Complete / Reopen** `x`
3. **Status ▸**: todo · doing · waiting · done · cancelled. Each status shows
   which column it moves the task to (per §3.3).
4. **Column ▸**: the current project's columns, with the current column checked.
   Hidden for Inbox tasks.
5. **Move to project ▸**: a type-to-filter list with recent projects first,
   then Inbox. When you pick a project you also pick its column in the same
   step: Enter accepts the default column, and → opens the column list.
6. **Due ▸**: Today · Tomorrow · This weekend · Next week · Pick date… · No date.
   The current value is shown.
7. **Priority**: an inline row of five swatches (none, low, medium, high,
   urgent), so one click sets it with no submenu. Keys `0`–`4`.
8. **Labels ▸**: a checkable, filterable list. Toggling a label keeps the menu
   open. You can create a new label from the filter text.
9. **Reminder ▸**: the presets from §8, plus Custom… and Remove.
10. **Duplicate** · **Copy link** · **Copy as markdown**
11. **Convert to note**
12. **Delete** `Del` (with an Undo toast)

**Behaviour:**

- Every action applies immediately and optimistically. A failed action rolls
  back and shows an error toast. Actions that remove a task from the current
  view (move, complete, delete, change due date) show an **Undo** toast for
  8 s. When a task leaves a filtered view, it fades out instead of vanishing.
- The pickers are **the same components** the just-added tray chips and triage
  use (§5.3, §5.4). There is one picker implementation per field.
- **Multi-select**: on desktop, `Cmd/Ctrl+click` toggles selection and
  `Shift+click` selects a range. On mobile, the sheet has a "Select" action
  that enters selection mode. Right-clicking inside a selection applies
  actions to every selected task. The menu header shows "12 tasks" and hides
  Open, Duplicate, and Convert. Bulk actions go through `POST /tasks/batch`
  as one undoable operation.
- The **native browser menu is kept** inside text inputs, editors, rendered
  links, and anywhere you hold `Shift` while right-clicking. Blair only takes
  over right-click on rows and cards.
- Accessibility: the menu uses ARIA menu semantics (Bits UI ContextMenu /
  DropdownMenu), arrow keys move through items, typing jumps to an item, and
  `Esc` closes one level at a time. The `⋯` button is the visible, discoverable
  path for people who don't know about right-click.
- **Other objects get their own menus** with the same mechanics:
  - Sidebar project: Rename, Colour/icon, Board/List default, Archive, Export
    project, Delete.
  - Kanban column header: Rename, Change status, WIP limit, Move left/right,
    Add column after, Delete (move tasks to…).
  - Note: Open, Pin/Unpin, Move to project, Convert to task, Copy as markdown,
    Delete.
  - Label: Rename, Colour, Delete.

## 5. Capture and triage — the core feature

This section has the strictest acceptance criteria in the spec.

### 5.1 Quick-add bar

- Present in every main view. Hotkeys `q` or `n` focus it from anywhere on
  desktop. `Esc` blurs it.
- **Context-aware defaults**: if you add a task inside a project, it goes to
  that project (first `todo` column, or the column you clicked "+ Add" in on
  the board). In **Today**, the due date defaults to today. In a **Label** view,
  the task gets that label. Otherwise the task goes to the Inbox.
- **Inline syntax** (parsed live, tokens highlighted as chips inside the input,
  each chip removable with one tap or Backspace):

| Token | Meaning | Example |
|---|---|---|
| `#name` | Project (fuzzy, autocomplete). Quote names with spaces: `#"Home lab"` | `#homelab` |
| `/name` | Column within the chosen/current project | `/doing` |
| `@name` | Label (creates it if new, after confirmation) | `@errands` |
| `!1`–`!4`, `!low` `!med` `!high` `!urgent` | Priority | `!high` |
| Natural date | `today`, `tonight`, `tomorrow`/`tmr`, weekday names, `next fri`, `in 3 days`, `in 2w`, `jun 3`, `3 jun`, `6/3`, `2027-06-03`, optional `at 5pm` / `17:00` | `fri at 9am` |
| `due:` | Explicit date prefix when natural detection is ambiguous | `due:may 4` |
| `\` | Escape the next token so it stays literal text | `\#1 fan` |

  Natural-date detection is **highlighted, not silent**. The detected phrase
  becomes a chip, and tapping the chip turns it back into plain text. Dates
  resolve in the user's timezone. A bare weekday means its next occurrence
  strictly after today (`tuesday` on a Tuesday means a week from today).
  `next <weekday>` means that weekday in the following calendar week.
  `tonight` means today at 20:00. A month and day that have already passed
  roll over to next year.
- **Unknown names**: `#newproj` with no match becomes a "create project
  newproj?" chip. It is confirmed with Enter before the task is created
  (API: `project_new` in the parse result; `POST /tasks` creates the project
  only when `create_missing: true`). A `/column` with no `#project` resolves
  against the current project view only.
- **Not tokens**: `#`, `@`, `/` and `!` count only at the start of a word
  (`C#`, `bob@example.com` and `and/or` stay literal). Markdown in the title is
  preserved.

- **Parser contract**: a single grammar, implemented in TypeScript (live
  preview) and Go (API `POST /tasks` with `"quick_add": "..."`, CLI). Both
  implementations must pass the shared vector file
  [`testdata/quickadd/cases.json`](../testdata/quickadd/cases.json). That file is
  the executable spec for the syntax. Both are fuzz-tested so they never panic,
  and the remaining title is never empty when the input had non-token text.

- **Submit**: `Enter` adds the task and keeps focus in the input for the next
  one. `Shift+Enter` (or the "Add & open" button) adds the task and opens its
  detail drawer. On mobile, the keyboard's return key adds the task, and a
  separate "Add & details" button sits beside it.

### 5.2 Mobile capture sheet

Opened by the **＋** tab, by the manifest shortcut, or by the share target
where supported. The sheet is a bottom sheet with the input autofocused and a
segmented toggle **Task | Note**. Below the input is a row of one-tap chips:
**Inbox ▾** (project), **Due**, **Priority**, **Label**. These apply to the
next task added. After you add a task the sheet **stays open** and the
just-added card appears at the top of the sheet (§5.3). Swipe down to close.
Note mode is a multiline markdown textarea with a Save button.

### 5.3 The just-added tray (never lose a task)

After any create (quick-add bar, capture sheet, or board "+"), the new task
appears **immediately** as a card in the **Just added** tray directly under the
input, with an entrance animation that draws the eye.

- Each card shows the rendered title and **tappable chips**: **Project**,
  **Column**, **Due**, **Priority**, **Labels**, and **Details →**. Tapping a
  chip opens a compact picker: a popover on desktop, a bottom sheet on mobile.
  Pickers are keyboard-navigable, with type-to-filter, recent projects first,
  and one-tap due shortcuts (Today, Tomorrow, This weekend, Next week, Pick…,
  None).
- **Changes from a chip apply instantly** (optimistic, with rollback on error)
  and update the card in place. The card stays in the tray until dismissed.
- The tray keeps the **last 5** tasks created in this tab session. Older ones
  collapse into "＋N more · View recently added". The tray clears on reload or
  when you dismiss it (×). The tasks themselves are unaffected.
- A **toast** confirms each add with **Open** and **Undo** (Undo deletes it
  outright; available 8 s).
- **Visibility rule (the "void" fix):** if the current view would not show the
  new task, its card shows why and how to get there. Examples: you are in
  **Today** and added a task with no due date, or you added `#work` while
  viewing Homelab. The card says *"Added to Work · not in Today"* and offers
  **[Go to it]** and **[Set due today]**. A create **never** produces a task
  the user can't immediately see and click.
- Desktop keyboard: after adding, `Tab` moves focus into the newest card.
  `p` project, `c` column, `d` due, `1`–`4` priority, `l` labels, `Enter`
  details, `Esc` back to input.

### 5.4 Inbox and triage mode

- Anything added without a project lands in the **Inbox**. The sidebar and tab
  bar show the Inbox count.
- **Triage mode** (`/triage`, `t` hotkey, or the "Triage N" button on the Inbox)
  shows one task at a time as a large card with:
  - big targets for **Project** (suggested: recent projects plus projects whose
    names or labels match words in the title, from simple local heuristics, no
    AI), **Column**, **Due** shortcuts, **Priority** 1–4, **Labels**;
  - actions: **File & next**, **Done**, **Delete**, **Skip**, **Open details**.
- Progress indicator "3 of 12". When the Inbox is empty: "Inbox zero" state.
- Keyboard: `j`/`k` next/previous, `p` `c` `d` `l`, `1`–`4`, `x` done,
  `#` delete, `s` skip, `Enter` file & next.
- Mobile: swipe left = skip, swipe right = file & next (only enabled once a
  project is chosen); buttons are always available as the accessible path.

### 5.5 Capture acceptance criteria (must pass Playwright e2e on desktop and mobile viewports)

1. Adding a task from any view shows it in the just-added tray within 100 ms
   (optimistic) and the card is clickable.
2. From the tray, the user can set project + column + due + priority with
   ≤ 2 taps each and without the input losing its place.
3. A task created in a view that filters it out shows the "not in this view"
   notice with a working **Go to it** link.
4. `Fix gutter #homelab /doing !high fri at 9am @house` creates a task titled
   "Fix gutter" with those fields set, in both the UI and via the API
   `quick_add` field.
5. With the network offline, adding a task shows it in the tray marked
   "pending sync", and it appears on the server after reconnecting (§12.3).
6. Triage files 10 Inbox tasks using only the keyboard.
7. Right-clicking a task (desktop) or long-pressing it (mobile) opens quick
   actions. The user can change column, status, project, priority and due date
   from that menu, and each change persists and can be undone.
8. Right-clicking a selection of 5 tasks and choosing **Move to project ▸ Work**
   moves all 5 in one batch request, and one Undo restores all 5.

## 6. Content and markdown

### 6.1 Titles

Inline markdown subset only: `**bold**`, `*italic*`, `` `code` ``,
`~~strike~~`, `[text](url)`, and bare URL autolinks. No block elements, images,
or raw HTML. Rendered in lists, cards, notifications and search results. The
editor shows source on focus and the rendered title on blur.

### 6.2 Descriptions and notes

GitHub-flavoured markdown: headings, lists, task-list checkboxes (clickable,
which writes the toggle back to the source), tables, fenced code with syntax
highlighting (lazy-loaded), blockquotes, links. No raw HTML.

### 6.3 Rendering safety

Markdown is stored as source and rendered **client-side** with `markdown-it`
(html disabled), then sanitized with **DOMPurify**. Links get
`rel="noopener noreferrer nofollow"` and `target="_blank"`. Only `http(s):` and
`mailto:` schemes are allowed. The API never returns server-rendered HTML.
A strict CSP is the second line of defence (§9.7).

## 7. Kanban board

### 7.1 Desktop

Columns side by side, horizontally scrollable. Each column has a header with
name, count, WIP limit warning (if set), a status colour dot, and a "+" to add
directly into that column, which uses the same tray behaviour. Drag cards
within and between columns. Drag column headers to reorder. Inline "＋ Column"
at the end asks for a name and status.

### 7.2 Mobile

One column per screen width with scroll-snap. Column pills at the top for
quick jumps. A long-press on a card does one of two things, depending on what
you do next:

- **Hold still** for 450 ms and the quick actions sheet opens (§4.4).
- **Start moving** after the press registers (more than 8 px of movement
  before release) and it becomes a drag. The sheet never opens.

Dragging near the screen edge pages to the next column. **Every drag action
also has a non-drag path**: the quick actions menu's Column and Move to project
items, for accessibility and reliability.

### 7.3 Ordering

`position` is a **fractional index** string (base-62, à la Figma), so a move
writes one row. The server rebalances a column's keys if any key exceeds 64
chars. Both TS and Go implementations share test vectors.

### 7.4 Done column behaviour

Cards in `done`/`cancelled` columns show completed styling. The column shows
the latest 20 and has a "Show all" link. Completed tasks older than 14 days are
hidden from the board by default (toggle), but are always in the Logbook.

## 8. Reminders and in-app notifications

- **No Web Push, no email** in v1. Notifications live inside the app, per account.
- Sources: a reminder fires; a task becomes overdue (once, at 09:00 local on
  the day after the due date — configurable or off);
  security events (new login from a new device, 2FA enabled or disabled, API
  token created).
- A **scheduler** goroutine ticks every 30 s, selecting due reminders with
  `fired_at IS NULL AND remind_at <= now`. It inserts notifications and marks
  reminders fired in one transaction (exactly-once per reminder).
- Delivery: **SSE** stream `GET /api/v1/events` pushes `notification.created`
  plus entity change events (`task.updated`, ...) so open tabs and devices stay
  in sync. The client reconnects with `Last-Event-ID`. Fallback is polling
  `GET /notifications?unread=true` every 60 s when SSE is unavailable.
- UI: a bell with an unread badge (sidebar on desktop, header on mobile),
  a notification panel, mark read / all read, and click-through to the task.
  While the app is open and visible, a fired reminder also shows a toast.
  The app does not use the OS Notification API in v1.
- Reminder UI in task details: presets (at due time, 15 min before, 1 h before,
  1 day before at 09:00) or a custom date/time. Relative reminders require a
  `due_time`, or use 09:00 for all-day tasks.

## 9. Accounts and security

Threat model: an internet-exposed, self-hosted app behind Caddy with TLS. The
attackers are credential stuffers, CSRF/XSS against a logged-in user, a stolen
API token, and a stolen database file. OWASP ASVS L2 is the reference
checklist. A security review against it is a Phase 9 exit criterion.

### 9.1 Bootstrap and registration

- On first start with no users, the server logs a **one-time setup URL**
  (`/setup?token=…`, valid 1 h, single use) to create the admin. Alternatively,
  `blair user create --admin --email …` creates the admin from the CLI.
- `BLAIR_REGISTRATION` = `closed` (default) | `invite` | `open`.
  - `invite`: an admin creates single-use invite links (7-day expiry, optional
    email lock).
  - `open`: public sign-up with stricter rate limits. Not recommended.
- The admin can disable or delete users, reset passwords (forces a change on
  next login), and reset 2FA. Admin actions are audit-logged.

### 9.2 Passwords

- **argon2id** (m=64 MiB, t=3, p=2, 16-byte salt, PHC string; parameters
  upgraded transparently on login).
- Minimum 12 chars, max 256. Checked against a bundled top-100k breached
  password list, offline. No composition rules.
- Password change requires the current password and revokes all other sessions.

### 9.3 Two-factor authentication

- **TOTP** (RFC 6238, SHA-1, 6 digits, 30 s, ±1 step), with a QR code and the
  secret shown for manual entry. Enabling it requires a valid code. The secret
  is stored **encrypted** (AES-256-GCM with a key derived from
  `BLAIR_SECRET_KEY`). Each code can be used once (the last step is stored to
  prevent replay).
- **10 recovery codes**, shown once, stored as argon2id hashes, single use.
  Regenerating them invalidates the old set.
- Login flow: `POST /auth/login` (email + password) → if 2FA is on, the
  response is `{"mfa_required": true}` with a short-lived (5 min)
  **pre-auth** cookie → `POST /auth/login/mfa` with `code` or `recovery_code`
  → full session. Errors never reveal whether the email exists.
- The admin can make 2FA mandatory for all users (`BLAIR_REQUIRE_2FA=true`).
- Passkeys (WebAuthn) are Phase 2.

### 9.4 Sessions (browser)

- Opaque random 256-bit token in the cookie `__Host-blair_session`
  (`Secure; HttpOnly; SameSite=Lax; Path=/`). Only the **SHA-256 hash** is
  stored. Sessions have a 30-day sliding expiry and a 90-day absolute expiry,
  and are rotated on login and privilege change.
- The session list in Settings shows device (parsed UA), approximate IP, and
  last seen, with **Revoke** and **Sign out everywhere**.

### 9.5 API tokens

- Personal access tokens with the format `blair_pat_<base62 32 bytes>` and a
  prefix for secret scanning. Shown once and stored hashed. Fields: name,
  scopes, optional expiry, last-used time.
- Scopes: `tasks:read`, `tasks:write`, `notes:read`, `notes:write`,
  `export`, `account:read`. Admin endpoints are **never** reachable
  by token.
- Sent as `Authorization: Bearer …`. Tokens are not accepted from query strings
  (except a separate, read-only `events` ticket for SSE: see §10.7).

### 9.6 Request protections

- **CSRF**: cookie-authenticated unsafe requests pass Go's
  `http.CrossOriginProtection` (Sec-Fetch-Site / Origin checks) **and** must
  carry `X-Requested-With: blair`. Bearer requests are exempt.
- **Rate limiting** (in-memory token buckets): login 5/min per IP and 10/hour
  per account with exponential backoff; MFA 5 attempts per pre-auth session;
  API 600/min per token or session. `429` responses carry `Retry-After`.
- **Trusted proxies**: client IP comes from `X-Forwarded-For` only when the
  peer is in `BLAIR_TRUSTED_PROXIES` (default `127.0.0.1/32,::1/128`).
- Request bodies are limited to 1 MiB by default and 20 MiB for batch endpoints. All
  input is validated against the OpenAPI schema.
- Timing-safe comparisons for tokens and codes.

### 9.7 Headers

`Content-Security-Policy: default-src 'self'; script-src 'self' 'sha256-…'
(SvelteKit hashes); style-src 'self' 'unsafe-inline'; img-src 'self' data: blob:;
connect-src 'self'; frame-ancestors 'none'; base-uri 'none'; form-action 'self'`,
plus `X-Content-Type-Options: nosniff`, `Referrer-Policy: same-origin`,
`Permissions-Policy` (camera, mic and geolocation off), and
`Cross-Origin-Opener-Policy: same-origin`. HSTS is set when
`BLAIR_BASE_URL` is https.

### 9.8 Data protection

- SQLite file permissions are 0600, and the data directory is 0700.
- Secrets at rest (TOTP) are encrypted. Credentials are hashed.
- An **audit log** records login success and failure, MFA events, password and
  2FA changes, token create and revoke, session revoke, admin actions, and
  batch writes over 100 ops, and exports. It is visible in Settings and retained 1 year.
- Account deletion hard-deletes all user rows (after password and 2FA
  confirmation). Export is offered first.

## 10. API

### 10.1 Principles

- **Contract-first**: [`api/openapi.yaml`](../api/openapi.yaml) (OpenAPI 3.0.3)
  is written or updated **before** handlers. Go server interfaces are
  generated with `oapi-codegen` (strict server), and the TypeScript client
  with `openapi-typescript` + `openapi-fetch` (ADR-0004). CI fails if the
  generated code is stale or the spec fails lint.
- **Documentation**: interactive reference at **`/api/docs`** (Scalar,
  self-hosted, no CDN), raw spec at `/api/openapi.yaml` and `.json`. Every
  operation has a summary, description, request and response examples, error
  examples, and required scopes. A "Getting started" section covers creating
  a token, a curl example, and pagination.
- **Contract tests**: every handler test validates requests and responses
  against the spec (kin-openapi), so the docs cannot drift from the code.

### 10.2 Conventions

- Base path `/api/v1`. JSON only (`application/json`), UTF-8, `snake_case` fields.
- Errors use **RFC 9457** `application/problem+json`:
  `{type, title, status, detail, instance, errors?: [{field, code, message}]}`.
  Stable `type` URIs (e.g. `https://blair.dev/problems/validation`), documented.
- `PATCH` uses JSON Merge Patch semantics (RFC 7396): omitted = unchanged,
  `null` = clear.
- List endpoints use **cursor pagination**: `?limit=50&cursor=…` (max 200),
  with the response `{ "data": [...], "next_cursor": "…" | null }`.
- Filtering: `?project_id=`, `inbox=true`, `status=todo,doing`, `label_id=`,
  `priority_gte=`, `due_from=`, `due_to=`, `overdue=true`, `q=` (FTS),
  `include_deleted=`, `updated_since=` (for sync), `sort=position|due|priority|created|updated`.
- Timestamps are UTC RFC 3339. `due_date` and `due_time` are local to the user's tz.

  "labels": ["…"], "version": 1, "parsed": { "tokens": [ … ] }, … }

### 10.5 Concurrency

Responses include `ETag: "v<version>"`. `PATCH` and `DELETE` accept `If-Match`.
A mismatch returns `412` with the current resource. The web client sends
If-Match on edits from the detail drawer and retries field-level merges
automatically when the fields don't overlap.

### 10.6 Idempotency

- Create requests may carry a client `id` (UUIDv7). Re-POSTing the same id by
  the same owner with identical content returns `200` with the existing
  resource. With different content it returns `409`. This makes offline-queue
  replays safe.
- The `Idempotency-Key` header is also honoured on the batch endpoints (24 h window).

### 10.7 Events (SSE)

`GET /api/v1/events` (cookie session, or a `?ticket=` from
`POST /events/ticket`: single use, 60 s, for token clients). Event types:
`task.created|updated|deleted`, `project.*`, `column.*`, `note.*`,
`notification.created`. Each event has an `id` (monotonic
per user) and a heartbeat comment every 25 s. A 5-minute replay buffer serves
`Last-Event-ID`.

## 11. Bulk API and export (agent-friendly migration)

Blair ships **no built-in importers**. Migrating from another app is a job for
a script or an AI agent: it reads the other app's export and writes through
the API. The API's job is to make that easy, safe to re-run, and lossless.

### 11.1 Bulk writes

- `POST /tasks/batch` (also `/projects/batch`, `/labels/batch`, `/notes/batch`)
  accepts up to 1000 operations: `{"op": "create"|"upsert"|"update"|"delete", ...}`.
  It runs in **one transaction**, so it is all-or-nothing, and returns a
  per-op result.
  `?dry_run=true` validates and returns the results without writing.
- **Upsert by external key**: every task, project, label and note accepts
  `external_source` + `external_id` (for example `vikunja` / `412`).
  `op: "upsert"` matches on that pair, so re-running a migration updates rows
  instead of duplicating them. `GET /tasks?external_source=vikunja` lists what
  came from where.
- **History is writable on create and upsert**: `created_at`, `completed_at`,
  and `status` (with `done` and `cancelled` kept exactly as given). This
  avoids the tududi problem, where completion dates were lost.
- **References inside a batch**: a create can name a `ref` ("p1"), and later
  ops in the same batch can point at `"project_ref": "p1"` /
  `"column_ref": "…"`. A project and its columns and tasks can then be made in
  one request without a round trip.
- Projects and columns can also be matched by name
  (`"project_name": "Homelab"`, case-insensitive), which suits quick scripts.
- **Validation errors** come back per op with field paths (RFC 9457
  `errors[]`), so an agent can fix and retry only the failed ops.

### 11.2 Export

- `GET /export?format=json` returns the full account as `blair.export.v1`:
  projects, columns, tasks (including completed and trashed), checklist,
  labels, reminders, notes, and settings. The format is versioned with a JSON
  Schema in `api/schemas/export.v1.json`. **Feeding an export back through the
  batch endpoints into an empty account reproduces the same data**
  (round-trip test).
- `format=csv` returns tasks only, one row per task: id, title, description,
  status, priority, project, column, labels (`;`-joined), due_date, due_time,
  created_at, completed_at.
- Settings → Data has download buttons. Exports are audit-logged.

### 11.3 Agent docs

The API docs include a **"Migrating into Blair" guide**. It covers the
recommended flow (export the source → map → dry run → batch upsert → verify
counts) and gives a mapping table for common apps: Vikunja, tududi, Todoist,
TickTick and Obsidian Tasks, covering statuses, priorities and buckets to
columns. It also includes a worked Python example using only the standard
library. The table is written so an agent can follow it.

## 12. PWA, mobile and offline

### 12.1 Install targets (all must be tested before v1)

| Platform | How | Caveats to handle |
|---|---|---|
| iOS / iPadOS Safari | Share → Add to Home Screen | No manifest shortcuts or share target. Use `apple-touch-icon` and status-bar meta. Storage may be evicted. Keep the outbox small and sync on open. |
| macOS Safari 17+ | File → Add to Dock | Runs as a standalone app window. Keyboard shortcuts must not collide with Safari's. |
| Android Firefox | Menu → Install / Add to Home screen | No share target or Background Sync. Manifest shortcuts are limited. Replay the outbox on `online` and app focus. |
| Android Chrome | Install prompt | Share target (`/share?title&text&url` → capture sheet) and shortcuts ("New task", "New note") enabled. |
| Desktop Chrome/Edge | Install icon | Same as Android Chrome. |

### 12.2 Manifest and shell

`name: Blair`, `display: standalone`, `start_url: /today?source=pwa`, theme and
background colours for light and dark, maskable icons (192, 512) and a
monochrome icon, `shortcuts`, and `share_target` (Chromium). The service worker
precaches the app shell and hashed assets, which makes repeat loads instant.
On a new version the user sees an "Update available — reload" toast (no
surprise reloads mid-typing).

### 12.3 Offline capture queue (ADR-0008)

- Creates for **tasks and notes** made while offline (or failing with a network
  error) go into an IndexedDB **outbox** with a client-generated UUIDv7. They
  show in the tray and lists marked ⟳ "pending sync".
- Replay happens in order on `online`, on `visibilitychange` → visible, at app
  start, and through Background Sync where available. Replays are idempotent
  (§10.6). A failed item (e.g. validation) stays in the outbox with an error
  badge and edit / discard options. Nothing is lost silently.
- Edits to pending items modify the queued payload. Edits to server items
  while offline are **not** supported in v1. The UI disables them with an
  "Offline — view only" banner.
- **Read cache**: the last successful responses for Inbox, Today, Upcoming,
  projects, and notes are cached in IndexedDB and shown while offline, with
  the "last synced" time.
- Logging out clears IndexedDB and caches.

## 14. Architecture

```
┌────────────── blair (single Go binary) ──────────────┐
│  chi router                                           │
│   ├─ /api/v1/*  oapi-codegen strict handlers          │
│   │     └─ service layer (business rules, invariants) │
│   │           └─ store (sqlc queries) ─► SQLite (WAL) │
│   ├─ /api/docs, /api/openapi.{yaml,json}              │
│   ├─ /healthz /readyz                                 │
│   └─ /*  embedded SvelteKit static build (SPA fallback)│
│  background: scheduler (reminders, overdue, purge,    │
│              backups), SSE hub, OpenTelemetry SDK     │
└───────────────────────────────────────────────────────┘
```

- **Backend**: Go (toolchain pinned in `mise.toml`), `chi`, `oapi-codegen`
  strict server, `sqlc` + `modernc.org/sqlite` (CGo-free), `pressly/goose`
  embedded migrations, `log/slog`, and the OpenTelemetry SDK for traces,
  metrics, logs and profiles (§14.2). See ADR-0002
  and ADR-0003.
- **Layering**: handlers (HTTP ↔ DTO only) → `service` (all rules: column/status
  invariants, ownership, quick-add, batch upserts) → `store` (sqlc). Services
  take an explicit `actor` (user id). Ownership is enforced in the store by
  always filtering on `owner_id`.
- **SQLite**: WAL, `busy_timeout=5000`, `foreign_keys=ON`, `synchronous=NORMAL`.
  A single writer connection plus a read pool. FTS5 virtual tables are kept in
  sync by triggers.
- **Frontend**: SvelteKit 2 + Svelte 5 (runes), TypeScript strict,
  `adapter-static` SPA mode, Tailwind CSS v4 with design tokens, Bits UI,
  `svelte-dnd-action` (touch-capable DnD), markdown-it + DOMPurify, a
  generated `openapi-fetch` client, and a SvelteKit service worker with an
  `idb` outbox (ADR-0005).
- **Packaging**: `web/build` → `internal/web/dist` → `go:embed`. A
  multi-stage Dockerfile produces a distroless `static:nonroot` image (< 30 MB).
- **CLI** (same binary): `blair serve | migrate | user create|passwd|reset-2fa|list |
  backup [--to path] | export --user | version`.

### 14.2 Observability (OpenTelemetry)

Blair is instrumented with the **OpenTelemetry Go SDK** from Phase 1 (ADR-0010).
All four signals are configured with the standard `OTEL_*` environment
variables, so any OTLP backend works (an OTel Collector, Honeycomb, Grafana,
and so on). With no endpoint set, the exporters are off and the overhead is
close to zero.

| Signal | How |
|---|---|
| **Traces** | `otelhttp` server middleware (route templates as span names, e.g. `PATCH /api/v1/tasks/{id}`); spans around service methods and SQLite queries (a thin `database/sql` wrapper, with query names from sqlc, never parameter values); spans for the scheduler, SSE fan-out and batch ops. W3C `traceparent` propagation. The web client sends a `traceparent` on API calls, so browser actions and server spans join one trace. |
| **Metrics** | OTel metrics over OTLP: HTTP RED (rate, errors, duration) by route, DB query duration, SQLite pool waits, scheduler lag, SSE connections, outbox replays, batch sizes, and Go runtime metrics. Optionally a Prometheus exporter on `/metrics` (`BLAIR_PROMETHEUS=true`, behind `BLAIR_METRICS_TOKEN`). |
| **Logs** | `log/slog` with the OTel slog bridge (`otelslog`), so logs carry `trace_id`/`span_id` and go out over OTLP. JSON logs are written to stdout as well. |
| **Profiles** | Continuous CPU, heap, goroutine and mutex profiles via the OTel profiles signal (OTLP) where the collector supports it. Until then, Pyroscope-compatible push with span-profile linking (`pprof` labels with the span ID). `net/http/pprof` sits on a separate localhost-only listener (`BLAIR_DEBUG_ADDR`, off by default). |

Rules:

- Resource attributes: `service.name=blair`, `service.version` (build info),
  and `deployment.environment`.
- **No PII or content in telemetry.** Task titles, note bodies, emails, tokens,
  and query parameters are never attributes or log fields. A user is
  identified by an opaque ID only. A test asserts that the span and log
  exporters never see a known secret or title in a request.
- Sampling: parent-based, with 100% by default for a single-user install,
  configurable through `OTEL_TRACES_SAMPLER`.
- `docs/OBSERVABILITY.md` (Phase 1) lists the span, metric and attribute names.
  These are a contract, just like the API.

volume `./data:/data`. The Caddy site `blair.wboll.dev { reverse_proxy

## 15. Quality and engineering practice

- **Spec-driven**: SPEC → OpenAPI → tests → code. Behavior changes update the
  spec in the same commit. ADRs record decisions.
- **TDD by default**. Go service and handler tests run against a real temporary
  SQLite DB (no DB mocks). Table-driven tests. `-race` in CI. Fuzz tests for the
  quick-add parser, fractional index, markdown-adjacent inputs, and batch
  payloads.
- **Test pyramid**: Go unit/integration (bulk) → API contract tests → Vitest
  for frontend logic (parser, outbox, stores) → Playwright e2e for critical
  journeys on Desktop Chrome, Desktop WebKit, Pixel 7 and iPhone 14 emulation,
  with axe checks.
- **Critical e2e journeys**: setup admin → enable 2FA → log out and in with TOTP;
  quick-add with syntax → file from tray; triage the Inbox by keyboard; kanban
  drag between columns (status changes); offline capture → sync; batch upsert
  a Vikunja-shaped fixture twice → no duplicates, completion dates intact;
  export → batch re-import round trip.
- **Static analysis**: `golangci-lint` (incl. `gosec`), `gofumpt`,
  `govulncheck`, `svelte-check`, ESLint, Prettier, `vacuum` (OpenAPI lint),
  `gitleaks`, `npm audit --omit=dev`.
- **Commits**: Conventional Commits enforced by `.githooks/commit-msg`; small,
  scoped commits; each commit builds and passes tests.
- **CI** (`.github/workflows/ci.yml`): lint → generate (verify no diff) → test
  → e2e → build image. Renovate/Dependabot for updates.
- **Definition of done** for any feature: spec updated, OpenAPI updated with
  examples, tests (unit + contract + e2e for UI journeys), works at 375 px and
  1440 px in light and dark, keyboard accessible, no axe violations, docs or
  CLAUDE.md touched if workflows changed.
